METHODS / BINARY REPAIR

方法与工具

二进制修复不是「一个工具给出答案」，而是一条证据链：定位、静态恢复、符号探索、 动态确认、差分验证与回归输入。每一环都只能回答一部分问题。

查看本机接入状态

修复链

  1. 01
    复现与定位

    先固定可重复的崩溃/错误输入，记下版本、环境与调用路径；没有复现就没有「修好了」。

  2. 02
    静态恢复

    用 Ghidra/Rizin/objdump 恢复函数边界与伪代码，标出缺陷区间与相邻控制流。

  3. 03
    符号探索

    angr/Triton 求「哪些输入能到达危险点」，把候选输入变成可检查的约束。

  4. 04
    动态确认

    Frida/GDB/QEMU 在真实或模拟环境里观察寄存器、内存和 API，确认路径确实发生。

  5. 05
    差分验证

    比较修复前后的二进制与行为：目标缺陷消失，其他行为没有意外变化。

  6. 06
    回归与模糊

    AFL++/syzkaller 找相邻路径与回归；通过不等于安全，只是没有发现新的反例。

工具矩阵

STATIC

Ghidra · Rizin · objdump

无头反编译、函数/符号恢复与静态证据。Route B 的 objdump/readelf 输出用于基线自检；它证明的是「观察到的字节与指令」，不是「行为正确」。

在本工作台：连接器 ghidra、rizin、binutils 会探测本机是否具备条件。

Ghidra ↗ Rizin ↗ binutils ↗
SYMBOLIC

angr · Triton

把「如何到达危险点」转成路径约束。适合边界清晰的小函数；路径爆炸、外部调用与并发会让模型失真。

在本工作台：angr、triton 作为 Python 模块接入；未安装时连接器显示「未检测到」。

angr ↗ Triton ↗
DYNAMIC

Frida · GDB · QEMU

运行时插桩、崩溃现场与跨架构模拟。动态证据最接近真实执行，但依赖环境、输入与观察点选择。

在本工作台：frida、gdb、qemu 探测 PATH；工具就绪只代表可以发起请求。

Frida ↗ GDB ↗ QEMU ↗
DIFF

Diaphora · BinDiff

把修复前后的二进制函数对齐，定位变化区间；差异本身不是正确性证明，但能暴露意外改动。

在本工作台：差分结果进入证据页，和契约、验收义务分开展示。

Diaphora ↗ BinDiff ↗
FUZZ

AFL++ · syzkaller

覆盖引导的输入生成，用于发现回归与相邻路径；内核/系统调用面适合 syzkaller，用户态目标适合 AFL++。

在本工作台：模糊测试是候选证据来源，不能替代人工契约与验收结论。

AFL++ ↗ syzkaller ↗
CONTAINMENT

Docker · 隔离运行

不可信样本应在容器或专用虚拟机里运行，限制网络、挂载与权限；工具就绪不等于沙箱配置正确。

在本工作台：连接器 docker 只探测 CLI，不自动启动容器。

验证要回答的四个问题

1. 缺陷真的复现了吗？

输入、版本、环境、崩溃信号必须可重复；不可复现的修复只是猜测。

2. 补丁只改了目标行为吗？

差分、回归用例与相邻路径检查；意外改动和未覆盖路径都要显式记录。

3. 证据来自哪一层？

静态、符号、动态、模糊各自有边界；不能把「模型说可以」当成运行结果。

4. 谁给出结论？

验收引擎按契约判定；助手、工具和页面都不自行宣布「已修复」。

证据成熟度与高级方法

全球修复研究正在从「生成一个补丁」转向「证明补丁在什么范围内、用什么证据成立」。 本工作台采用同一方向：先记录可复核的观察，再谈覆盖与验收。

层级回答的问题本工作台实现仍不能证明
V0缺陷是否真实存在？调用点/边界是否正确？原始 SHA、契约、静态 gate、修改区域运行时可达性
V1–V2哪些输入能到达危险点？约束是否可满足？symbolic/dynamic gate 透传；缺失保持 unknown全覆盖路径、并发/外部调用
V3真实运行时是否触发、修复后是否消失？动态 gate、valid/invalid 用例、ASan 类观察所有输入、所有环境
V4目标函数内的安全性是否成立？verification/compatibility 字段；模型级结论只读全程序形式化等价
V5只改目标行为吗？其他行为是否异常？行为对比 cases、summary、not_claimed完整行为等价/生产批准

已落地的升级

  • 证据控制室：总览、V0–V5 矩阵、义务筛选、Attempts、产物指纹、原始 JSON。
  • 只读评估 API：/api/jobs/{id}/evaluation 输出覆盖率、缺口与可观测性指数；不是 verdict。
  • 失败即显式：缺失、not_run、无分母均为 N/A/缺口，绝不折叠成通过。
  • 研究映射：把 SSDF、CWE、SLSA、in-toto、差分/符号/模糊测试映射到可检查字段。

下一步的工程化路线

  • 接入 Alive2/CBMC 做补丁等价/内存安全证明，而不是只靠测试。
  • 把 SLSA/in-toto provenance 与证据包绑定，支持可复现构建。
  • 建立 ARVO/CVEfixes/Vul4J 回归基准，报告 precision/recall/成本/时延。
  • 符号/动态/模糊工具由本机连接器按需启用；未安装时保持 unknown。

评估口径：可观测性指数 = 0.35×证据覆盖 + 0.25×义务通过率 + 0.20×用例通过率 + 0.10×产物完备 + 0.10×行为对比。它只衡量证据覆盖，不替代验收引擎。

参考与延伸

  • NIST SP 800-218 SSDF：安全软件开发生命周期与验证实践。
  • CWE / CWE Top 25：漏洞分类与修复口径。
  • OWASP Top 10：应用层风险与修复建议。
  • SLSA v1.0 / in-toto：构建来源与供应链证据。
  • OpenSSF Scorecard：开源项目安全实践度量。
  • OSS-Fuzz / AFL++：持续模糊与回归。
  • CVEfixes / Vul4J / Defects4J：修复基准与回归数据。
  • Alive2 / CBMC：翻译验证/有界模型检查。
  • 本项目仓库：实现、测试与架构说明。

工具会变化，方法链不变：先复现，再定位，再提出候选，最后用独立证据验证。 本页的方法说明不构成对任何样本「已修复」的结论。
